# 原系統搬遷研究

客戶要用 AI GO **取代一套正在用的系統**（例：104 人資後台、某套進銷存或排班 SaaS）時照這份做。
這類系統通常沒有程式碼可搬，只有「畫面＋資料」，所以研究方式是：**客戶在自己的 Chrome 登入原系統，
你用 Chrome 擴充套件逐頁看、逐頁讀**，再把結果交給 aigo-builder 的遷入流程變成規格、資料結構與分批實作。

**技術做法照 aigo-builder 遷入線**（`references/migration-workflow.md`）：產品線判斷（沒有程式要搬的 SaaS 屬 §2.1 問題零的第三種，
產品線照新建線判）、資料對應（§2.4）、匯入前的對應表確認（§2.5）、寫入正式資料的閘門（`data-operations.md` §3.5）。
本檔補的是**怎麼研究原系統、怎麼分段帶客戶走完**。

開口指南 PDF 的「原系統搬遷任務」那段提示詞就是本流程的入口；客戶只說「我們要把某某系統換掉」也走這裡。

## 研究原系統的習慣

- **研究時只看不改**：研究階段只讀畫面、只匯出；要在原系統按任何會改東西、會通知別人的按鈕（新增、送出、寄信、改設定），先問客戶。
- **登入是客戶自己來**：客戶在 Chrome 登入；登出了就請他重新登入。手機驗證碼也是客戶處理。
- **真實資料放 repo 以外**：匯出檔、讀出來的資料、含個資的截圖放工作區的 `exports/<原系統代號>/`
  （`setup.md` §3；原系統代號用簡短英數，例：`104`），底下分 `files/`、`screens/`、`notes/`。
  寫進專案的規格與對應表用欄位名稱與虛構範例。
- **匯出前先講**：每次要匯出或下載，先講要匯出什麼、哪段期間、存到哪，客戶說好再按。
- **逐頁讀取要節制**：沒有匯出功能才逐頁讀，一次一頁慢慢翻。出現驗證碼或流量限制就停下來跟客戶說，
  改用官方匯出或請客戶向廠商要資料（驗證碼要客戶自己處理）。
- **每一段做完先給客戶看**，客戶說可以才往下一段。客戶可以隨時說「先停在這裡」，下次用「接續上次的搬遷」回來。

## 0. 準備：Chrome 擴充套件與登入

1. **確認擴充套件連上了**：
   - Claude Code：看得到 Chrome 擴充套件的工具（`mcp__claude-in-chrome__*`）且能列出分頁。沒有 → 請客戶裝
     Claude 擴充套件（https://chromewebstore.google.com/detail/claude/fcoeoabgfenejglbffodgkkbkcdhcgfn ，
     需要 Claude 付費方案），用同一個 Claude 帳號登入；終端機版可輸入 `/chrome` 連線。
   - Codex：用 `@Chrome` 呼叫。沒有 → 請客戶在 Codex 桌面版的外掛（Plugins）加入 Chrome，照畫面裝好 OpenAI 的擴充套件
     （https://chromewebstore.google.com/detail/codex/hehggadaopoacecdllhhajmbjkdcmajg ，
     官方說明 https://learn.chatgpt.com/docs/chrome-extension ），在 Chrome 看到「已連線」。
   - 裝不起來 → 請工程師一起看（`engineer-collab.md` §3.1）。
2. **確認客戶已在 Chrome 登入原系統**：打開原系統網址看是不是登入後的畫面。
3. **問清楚**（可以一次列出，照編號回答）：原系統叫什麼、網址；要由哪一支 AI GO 系統接手，或要開新的；
   誰在用原系統（哪些角色）；預計什麼時候停用、合約何時到期。
   客戶在某支專案的資料夾裡卻說「開新的」→ 講清楚兩者差別（加在現有的 vs 新開一支，見 `builder-guide.md` §4），讓客戶選。
4. 建好 `exports/<原系統代號>/`，告訴客戶資料會放在哪。

## 1. 功能研究

逐一點開每個選單與子頁（只看），列出：

| 項目 | 要記下的 |
|---|---|
| 選單與畫面 | 每個畫面叫什麼、在哪個選單下、做什麼用 |
| 欄位 | 每個表單／列表有哪些欄位、必填、選項清單、格式（日期、金額、身分證） |
| 流程 | 送出 → 誰核准 → 結果；狀態有哪幾種、怎麼轉換 |
| 報表與匯出 | 有哪些報表、條件、能匯出成什麼格式 |
| 通知 | 什麼時候寄信、推播、提醒誰 |
| 角色與權限 | 有哪些角色、各看得到／改得到什麼 |
| 自動計算 | 系統自己算的數字（年資、特休天數、加班費、薪資）——算法請客戶確認，看畫面推的標「推測」 |

截圖存 `screens/`，報告寫 `notes/功能盤點.md`。**給客戶看**：「選單 → 功能 → 一句話用途」的清單，問「有沒有漏掉你們常用的？哪些其實沒在用？」

## 2. 歷史資料：匯出或讀取

1. 列出原系統裡有哪些**資料種類**（員工、部門、出勤、請假、薪資……）、各約多少筆、最早到什麼時候。
2. 跟客戶決定**要搬哪些、哪段期間**。不搬的寫下理由與保存方式（例：舊資料匯出成檔案留存）。
3. 取得方式依序：**官方匯出**（Excel／CSV）＞ 原系統提供的 API（要金鑰的照 builder 外部服務做法，`builder-guide.md` §7）＞
   **逐頁讀取**。附件（照片、合約 PDF）另列清單，問客戶要不要搬。
4. 檔案存 `files/`，檔名寫清楚資料種類與期間。**核對筆數**：原系統畫面上的總筆數＝檔案筆數，對不上就找原因。
5. **給客戶看**：資料清單（種類、期間、筆數、取得方式、檔名），不貼內容。

## 3. 資料怎麼進 AI GO（builder 遷入線 §2.4、§2.5）

照 builder 做**對應表**：每種資料 → AI GO 的哪本帳冊（平台內建的優先，例：員工對 `hr_employees`）→ 每個欄位對到哪一欄、
格式怎麼轉、對不上的怎麼處理（捨棄／放備註欄／新增欄位）。

- **舊編號 → 新編號**：每筆保留原系統的編號（例：`legacy_id`），之後比對、補匯、追查都靠它。
- **主資料先、交易資料後**（先員工、部門，再出勤、請假）。
- 對應表寫進專案文件（照專案 `AGENTS.md` 的文件位置）。
- **用白話給客戶看**，一次講一種資料：「原系統的『到職日』會放到 AI GO 員工資料的『到職日』；原系統的『職等』AI GO 沒有，打算…」。
  客戶確認對應表，就是 builder §2.5 要的確認。
- **匯入照 builder 的寫入閘門**（`builder-guide.md` §5）：算筆數 → 備份 → 先匯 1 筆給客戶看 → 客戶說可以再匯其餘；匯完核對筆數並抽查幾筆。
- 動到別支系統也在用的帳冊，或專案列在「希望先知會」的 → 知會工程師（`engineer-collab.md` §3.2）。

## 4. 值得保留的功能

把第 1 段的功能分三類給客戶，每項一句理由：

- **原系統做得好、AI GO 也要有**（例：「請假時自動顯示剩餘特休」）
- **用起來不方便、不要照搬**（例：「核准要點三層選單」）→ 記下更好的做法
- **其實沒在用**

客戶分成 **一定要 ／ 最好有 ／ 不需要**。AI GO 現有系統已經有的，標「已有，只需確認」。

## 5. 規格書與資料結構（builder Phase 1.5）

依客戶勾選的內容照 builder 寫計畫（需求、app 分配、授權架構、資料承載、模板盤點），寫進專案文件；每個功能另寫一段驗收情境（第 7 段要照著點）。
分批：主資料先，每批做完都能單獨用。用 `builder-guide.md` §3 的白話摘要跟客戶確認，改不回來的選擇用 §4 講清楚。

## 6. 衝突點

一條一條列出，每條給 **2～3 個做法、各自的結果、你的建議**，讓客戶決定；決定照專案的方式記下來。常見來源：

| 來源 | 例 |
|---|---|
| AI GO 現有功能或之前定的規則 | 原系統特休用到職日制，AI GO 這支之前定的是曆年制 |
| 別支系統也在用的資料 | 員工資料做帳工作台也在讀，改欄位會連帶影響 |
| 原系統做法 vs 實際做法 | 系統裡設三層核准，實際上只有主管核准 |
| 資料本身 | 同一人兩筆資料、舊資料必填欄位是空的、格式不一 |
| 平台做法不同 | 原系統有的功能，AI GO 要用別的方式做 |

## 7. 分批實作與驗收

每一批照 builder 主流程做，加上本 skill 的給客戶看與操作驗收，另外：

- **新舊比對**：挑同一筆資料，在原系統與 AI GO 各看一次，核對畫面上的數字與狀態一致（例：同一位員工的剩餘特休）。
- 自動計算的功能至少比對三種情況（一般、邊界、例外）。對不上 → 先問客戶哪邊才對。

## 8. 切換計畫

最後一批上線前，跟客戶一起定好並寫進專案文件：

- **並行期**：新舊系統同時用多久、這段期間資料以哪邊為準
- **切換日**：哪天開始只用 AI GO；切換前**最後一次匯出**（補匯並行期間的新資料）
- **停用原系統**：誰負責、合約何時到期；停用前要留存的檔案
- **出問題怎麼辦**：切換後一週內有問題，暫時回原系統還是在 AI GO 修
- **`exports/` 怎麼處理**：搬完後保留多久、誰負責刪（裡面有個資）

## 回報格式（每一段結束時）

三句以內：這段做了什麼、要客戶確認的一件事、下一段要做什麼。細節放在 `notes/` 或專案文件，客戶要看再給。
