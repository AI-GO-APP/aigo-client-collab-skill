# 原系統搬遷任務

客戶要用 AI GO **取代一套正在用的系統**（例：104 人資後台、某套進銷存或排班 SaaS）時照這份做。
原系統通常沒有程式碼可搬，只有「畫面＋資料」，所以研究方式是：**客戶在自己的 Chrome 登入原系統，
你用 Chrome 擴充套件逐頁看、逐頁讀**，再把結果變成 AI GO 的規格、資料結構與分批實作。

技術判斷照 aigo-builder：產品線（`references/product-line-decision.md`；沒有程式要搬的 SaaS 屬於
`references/migration-workflow.md` §2.1 問題零的第三種，產品線照新建線判）、資料落點（同檔 §2.4）、
匯入閘門（同檔 §2.5：對應表沒產出、沒經確認前不匯入任何資料）。本檔只管**怎麼帶客戶走完**。

開口指南 PDF 的「原系統搬遷任務」那段提示詞就是本流程的入口；客戶只說「我們要把某某系統換掉」也走這裡。

## 硬規則（整個任務都適用）

1. **對原系統唯讀**：不新增、不修改、不刪除、不送出表單、不寄信、不改設定、不按會通知別人的按鈕。
   不確定某個按鈕會不會改東西 → 不按，問客戶。
2. **登入是客戶的事**：你不輸入帳密、不處理兩步驟驗證、不建立帳號。登出了就請客戶重新登入。
3. **真實資料不進專案**：匯出檔、讀出來的資料、含個資的截圖一律放客戶電腦的**搬遷資料夾**
   （預設 `~/aigo-migration/<原系統代號>/`，底下 `exports/`、`screens/`、`notes/`），**不放進專案資料夾、不進任何 repo、
   不貼進 issue 或 PR**。寫進專案的規格與對應表只用欄位名稱與虛構範例。
4. **匯出前先問**：每次要按「匯出」或下載檔案，先講要匯出什麼、哪段期間、存到哪，客戶說好才按。
5. **逐頁讀取要節制**：沒有匯出功能才逐頁讀；一次一頁、慢慢翻，不同時開很多分頁狂讀。
   原系統的使用條款不允許自動讀取、或出現驗證碼／流量限制 → 停下來，改用官方匯出或請客戶向廠商要資料，**不繞過驗證碼**。
6. **每一段做完先給客戶看**，客戶說可以才往下一段。客戶隨時可以說「先停在這裡」，下次用「接續上次」回來。
7. 紅線照 SKILL.md；搬遷常碰到的是**資料結構（建表、引用平台預設表、共用資料）**與**正式資料整批匯入**，
   這兩項一定經工程師（見第 3、5 段）。

## 0. 準備：Chrome 擴充套件與登入

1. **確認擴充套件連上了**：
   - Claude Code：看得到 Chrome 擴充套件的工具（`mcp__claude-in-chrome__*`）且能列出分頁。沒有 → 請客戶裝
     Claude 擴充套件（Chrome 線上應用程式商店 https://chromewebstore.google.com/detail/claude/fcoeoabgfenejglbffodgkkbkcdhcgfn ，
     需要 Claude 付費方案），用同一個 Claude 帳號登入；終端機版可輸入 `/chrome` 連線。
   - Codex：用 `@Chrome` 呼叫。沒有 → 請客戶在 Codex 桌面版的外掛（Plugins）加入 Chrome，照畫面裝好 OpenAI 的擴充套件
     （商店頁 https://chromewebstore.google.com/detail/codex/hehggadaopoacecdllhhajmbjkdcmajg ，
     官方說明 https://learn.chatgpt.com/docs/chrome-extension ），在 Chrome 看到「已連線」。
   - 都裝不起來 → 不要改用別的瀏覽器硬做；走「交給工程師」。
2. **確認客戶已在 Chrome 登入原系統**：打開原系統網址看是不是登入後的畫面；不是就請客戶自己登入，
   跟他說「密碼只在瀏覽器的登入頁輸入，不要打在對話框裡」。
3. **問清楚四件事**（一次一題）：原系統叫什麼、網址；要由哪一支 AI GO 系統接手（或要開新的）；
   誰在用原系統（哪些角色）；預計什麼時候停用原系統、有沒有合約到期日。
4. 建好搬遷資料夾，告訴客戶資料會放在哪。

## 1. 功能研究

逐一點開每個選單與子頁（只看不改），列出：

| 項目 | 要記下的 |
|---|---|
| 選單與畫面 | 每個畫面叫什麼、在哪個選單下、做什麼用 |
| 欄位 | 每個表單／列表有哪些欄位、必填、選項清單、格式（日期、金額、身分證） |
| 流程 | 送出 → 誰核准 → 結果；狀態有哪幾種、怎麼轉換 |
| 報表與匯出 | 有哪些報表、條件、能匯出成什麼格式 |
| 通知 | 什麼時候寄信、推播、提醒誰 |
| 角色與權限 | 有哪些角色、各看得到／改得到什麼 |
| 自動計算 | 系統自己算的數字（年資、特休天數、加班費、薪資）——**算法要請客戶確認**，看畫面猜的要標「推測」 |

- 截圖存 `screens/`（含個資的先遮或不存），報告寫 `notes/功能盤點.md`。
- **產出給客戶看**：用「選單 → 功能 → 一句話用途」的清單，問「有沒有漏掉你們常用的？哪些其實沒在用？」

## 2. 歷史資料：匯出或讀取

1. 列出原系統裡有哪些**資料種類**（員工、部門、出勤、請假、薪資……）、各約多少筆、最早到什麼時候。
2. 跟客戶決定**要搬哪些、哪段期間**（例：在職與近三年離職員工、近兩年出勤）。不搬的寫下理由與保存方式
   （例：舊資料匯出成檔案留存，不進 AI GO）。
3. 取得方式依序：**官方匯出**（Excel／CSV）＞ 原系統提供的 API（要金鑰的屬紅線，交給工程師）＞ **逐頁讀取**
   （照硬規則 5）。附件（照片、合約 PDF）另列清單，問客戶要不要搬。
4. 檔案存 `exports/`，檔名寫清楚資料種類與期間。**核對筆數**：原系統畫面上的總筆數 = 檔案筆數，對不上就找原因。
5. **產出給客戶看**：資料清單（種類、期間、筆數、取得方式、檔名），不貼內容。

## 3. 資料怎麼進 AI GO

照 aigo-builder `migration-workflow.md` §2.4 做**對應表**：每種資料 → AI GO 的哪張表（平台預設表優先，例：員工對
`hr_employees`）→ 每個欄位對到哪一欄、格式怎麼轉、對不上的怎麼處理（捨棄／放備註欄／新增欄位）。

- **舊編號 → 新編號**：每筆資料保留原系統的編號（例：`legacy_id`），之後比對、補匯、追查都靠它。
- **主資料先、交易資料後**（先員工、部門，再出勤、請假）。
- 對應表寫進專案的文件（照專案 `AGENTS.md` 的文件位置），只放欄位與虛構範例。
- **用白話給客戶看**：「原系統的『到職日』會放到 AI GO 員工資料的『到職日』；原系統的『職等』AI GO 沒有，打算……」，
  一次講一種資料，客戶確認。
- **工程師複核**：對應表涉及新建資料表、引用平台預設表、或別支系統也在用的資料 → 開「需要技術支援」issue
  請工程師複核資料結構，**核可前不建表、不匯入**。
- **試匯入**：工程師核可後，先用 3～5 筆（可用虛構化後的資料）匯到測試環境或測試帳套，客戶在畫面上看過正確。
- **正式整批匯入交給工程師**（紅線：一次匯入大量正式資料），issue 附對應表位置、檔名、各檔筆數（不附檔案本身），
  匯完核對筆數並抽查幾筆。

## 4. 值得保留的功能

把第 1 段的功能分三類給客戶勾選，每項一句話講理由：

- **原系統做得好、AI GO 也要有**（例：「請假時自動顯示剩餘特休」）
- **用起來不方便、不要照搬**（例：「核准要點三層選單」）→ 記下更好的做法
- **其實沒在用**

客戶分成 **一定要 ／ 最好有 ／ 不需要**。AI GO 現有系統已經有的功能，標「已有，只需確認」。

## 5. 規格書與資料結構

依客戶勾選的內容寫規格，寫進專案文件（照專案 `AGENTS.md`；有需求或待辦文件就接在那裡）：

- **每個功能**：誰用、哪個畫面、流程（含例外）、做完看到什麼、驗收情境（第 7 段要照著點的步驟）
- **資料結構**：第 3 段的對應表＋新功能需要的欄位與關聯
- **權限**：哪些角色看得到／改得到什麼（權限屬紅線：規格寫清楚，實作交給工程師）
- **分批**：哪幾批、先後順序與理由（主資料先；每批做完都能單獨用）

給客戶看規格的白話摘要（每個功能三句：誰、做什麼、看到什麼），確認後再往下。

## 6. 衝突點排解

一條一條列出衝突，每條給 **2～3 個做法、各自的結果、你的建議**，讓客戶決定；決定照專案的決策紀錄方式記下來。
常見的衝突來源：

| 來源 | 例 |
|---|---|
| AI GO 現有功能或既有決定 | 原系統特休用到職日制，AI GO 系統之前定的是曆年制 |
| 其他系統共用的資料 | 員工資料別支系統也在讀，改欄位會連帶影響 |
| 原系統做法 vs 實際做法 | 系統裡設三層核准，實際上只有主管核准 |
| 資料本身 | 同一人兩筆資料、必填欄位舊資料是空的、格式不一 |
| 平台限制 | 原系統有的功能平台做不到或要另外設定 |

會改掉既有決定的，照 SKILL.md A 的第 2 步問一次；影響其他系統或碰到紅線的，交給工程師。

## 7. 分批實作與驗收

每一批照 SKILL.md 的 **A 功能**第 4～10 步做，驗收除了 A 第 6 步（E2E 或介面操作驗收）之外，再加：

- **新舊比對**：挑同一筆資料（測試資料或客戶同意的一筆），在原系統與 AI GO 各看一次，核對畫面上的數字與狀態一致
  （例：同一位員工的剩餘特休）。只讀原系統，不在原系統操作。
- 自動計算的功能至少比對三種情況（一般、邊界、例外）。對不上 → 先問客戶哪邊才對，不要自己決定。

## 8. 切換計畫

最後一批上線前，跟客戶一起定好並寫進專案文件：

- **並行期**：新舊系統同時用多久、這段期間資料以哪邊為準
- **切換日**：哪天開始只用 AI GO；切換前**最後一次匯出**（補匯並行期間的新資料）
- **停用原系統**：誰負責、合約何時到期；停用前要留存的檔案
- **出問題怎麼辦**：切換後一週內有問題，暫時回原系統還是在 AI GO 修
- **搬遷資料夾怎麼處理**：搬完後保留多久、誰負責刪（裡面有個資）

## 回報格式（每一段結束時）

三句以內：這段做了什麼、要客戶確認的一件事、下一段要做什麼。細節放在 `notes/` 或專案文件，客戶要看再給。
