# 給技術端：讓一個專案開放客戶協作

客戶的 AI 會讀專案的 `AGENTS.md`。在裡面加一節「客戶協作」，本 skill 就會照它調整紅線、指派 issue、找正式網址。
Claude Code 讀的是 `CLAUDE.md`，確認它有 `@AGENTS.md` 這一行。

## 範本（貼進 `AGENTS.md`）

```markdown
## 客戶協作

本 repo 開放客戶以 AI Coding 協作（skill：`aigo-client-collab`）。使用者是客戶（非程式背景）時，
一律照該 skill 的說話規則與流程，技術操作照本檔與 aigo-builder。

- 技術窗口（issue 指派對象）：@<GitHub 帳號>
- 客戶可以自己發布：是（照本檔「發布流程」；發布前核對線上版本）
- 正式網址：
  - <App 名稱>：<網址>
- 紅線增加：<本專案額外要交給工程師的，例：「文中寫回相關」「`hr_employees` 欄位用法」>
- 紅線放寬：<本專案允許客戶自己做的，例：「新增假別」；沒有就寫「無」>
- 客戶測試用資料：<本機驗收環境或測試帳套的說明；沒有就寫「無，先看草稿版」>
```

## 開放前檢查

- 客戶的 GitHub 帳號已加進 repo（Write 權限；要開 PR、issue 與合併）。
- 客戶的 AI GO 帳號有發布這支 app 的權限；沒有就不要在上面寫「可以自己發布：是」。
- 本機檢查（測試、型別檢查）有一支指令就能跑完，寫在 `AGENTS.md` 的指令區——客戶的 AI 會照著跑。
- 發布工具有「發布前核對線上版本」的保護（例：拒絕覆蓋不在自己歷史裡的版本）。沒有的話，客戶與你同時發布會互相蓋掉。
- repo 沒有會讓客戶誤用的舊流程說明（例：已停用的 CI 發布）。

## 開研究任務給客戶

照 `references/issue-format.md` 的「研究任務」格式寫，加標籤 `研究任務`、指派客戶的 GitHub 帳號，
再把 issue 網址傳給客戶，請他貼給 AI：「請讀這個 issue 開始研究：<網址>」。
