# 給技術端：讓一個專案開放客戶協作

客戶的 AI 會讀專案的 `AGENTS.md`。在裡面加一節「客戶協作」，本 skill 就知道找誰、哪些事要先知會你、用什麼測試資料、正式網址在哪。
Claude Code 讀的是 `CLAUDE.md`，確認它有 `@AGENTS.md` 這一行。

這一節**不是限制清單**：客戶的 AI 照 aigo-builder 與本檔的做法做事，builder 在重要操作前本來就會停下來確認。
這一節寫的是「怎麼一起合作最順」。

## 範本（貼進 `AGENTS.md`）

```markdown
## 客戶協作

本 repo 開放客戶以 AI Coding 協作（skill：`aigo-client-collab`）。使用者是客戶（非程式背景）時，
照該 skill 用白話引導；做法照本檔與 aigo-builder。

- 工程師（請協助、知會、請審閱的對象）：@<GitHub 帳號>
- 正式網址：
  - <App 名稱>：<網址>
- 希望先知會的事（在 PR 或 issue @我一聲，照常進行，不用等我回覆）：
  - <例：改到做帳工作台也在用的員工欄位>
  - <例：動到算錢的規則>
- 測試資料：<驗收用的測試帳號、測試資料或本機驗收環境；正式網址驗收可以用的測試資料，例：名稱前加「測試」的員工>
- 其他協作習慣：<例：PR 合併前請我看一眼的情況；沒有就寫「無」>
```

## 開放前檢查

- 客戶的 GitHub 帳號已加進 repo（Write 權限；要開 PR、issue 與合併）。
- 客戶的 AI GO 帳號有這支 app 需要的權限（開發、發布用 `builder.access`；邀請、改角色另有權限，見 aigo-builder `member-admin.md`）。
- 本機檢查（測試、型別檢查）有一支指令就能跑完，寫在 `AGENTS.md` 的指令區——客戶的 AI 會照著跑。
- 專案的工具找 aigo-builder 與工作區時，客戶的配置是 `~/aigo-projects/<租戶>/<repo>`、skill 在 `~/.agents/skills/`
  （見 `setup.md` §3）；工具要能在這個配置下跑。
- 發布工具有「發布前核對線上版本」的保護（例：拒絕覆蓋不在自己歷史裡的版本），客戶與你同時發布才不會互相蓋掉。
- repo 沒有會讓客戶誤用的舊流程說明（例：已停用的 CI 發布）。

## 開研究任務給客戶

照 `references/engineer-collab.md` §5 的格式寫，加標籤 `研究任務`、指派客戶的 GitHub 帳號，
再把 issue 網址傳給客戶，請他貼給 AI：「請讀工程師發來的這個請求，開始研究：<網址>」。
