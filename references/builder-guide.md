# 照 builder 做，用白話講

aigo-builder 決定**做什麼、怎麼做、什麼時候要停下來確認**；這份只管**怎麼跟客戶講**。
每一節對應 builder 的一個環節，給問法與確認的範本。範本是參考，照情況改寫，比喻照 `metaphors.md`。

確認類的範本都有同樣三件事：**會發生什麼、誰會受影響、能不能改回來**。客戶回「同意」「好」「可以」就是 builder 要的確認；
回「等一下」「我想想」就停，問他想先弄清楚哪一點。

## 1. 開始做之前（builder Phase 0：看現有系統）

builder 要先看線上版本、既有的帳冊、定時工作。跟客戶說一句就好：

> 我先看一下這支系統現在的樣子（線上的版本、已經有哪些資料表），大概一兩分鐘，看完跟你說我們要從哪裡改。

需要平台登入時，照 `setup.md` §5 帶客戶登入，再說：「登入好了，密碼只存在你的電腦，我不會看到。」

看完如果發現客戶要的功能**其實已經有了**（例：欄位已經在，只是清單上沒顯示），先講你看到的，再問他卡在哪：

> 我看了一下，「員工名冊」的編輯畫面其實已經有「緊急聯絡人」。你遇到的是哪一種？
> 1. 欄位有，但大部分人沒填　2. 有填，但清單上看不到　3. 其他，我自己說

## 2. 問需求（builder Phase 1.5 §1.0 四問）

照 builder 一輪問完，寫成白話、編號、附選項；客戶已經說過的不重問：

> 為了做對，我先問四件事，你照編號回答就好，不確定的寫「不確定」：
> 1. **誰會用？** 例：只有人資／所有同事／主管／事務所的客戶
> 2. **要做什麼？** 用你的話描述一次操作：誰在哪個畫面、按了什麼、之後看到什麼。有沒有現在的做法可以參考（紙本、Excel、別的系統）？
> 3. **要不要讓外面的人不登入就看得到？** 例：公開的報名頁、官網。大多數內部系統是「不用」
> 4. **有沒有特別的需求？** 例：要定時自動做某件事、要接 LINE 或別的系統、要上傳檔案

問題三、四對大部分功能答案都是「不用／沒有」，可以把預期答案寫在後面讓客戶確認（「我猜是不用，對嗎？」）。

## 3. 計畫的白話摘要（builder 計畫閘門）

builder 的計畫有好幾張表（需求、模板、app 分配、授權、資料承載）。表照 builder 寫在專案文件或對話裡給需要的人看；
跟客戶確認時用這個摘要：

> 我打算這樣做，你看對不對：
> - **誰用、做什麼**：<一兩句>
> - **做完你會看到**：<畫面上多了什麼、按了會怎樣>
> - **資料放哪**：<例：放在平台內建的「員工」帳冊／新做一本「教育訓練紀錄」帳冊>
> - **誰看得到**：<例：所有同事都能填，只有人資看得到全部>
> - **要不要新開一支系統**：<不用，加在現有的／要，因為…>
> - **我會怎麼驗收**：<實際操作哪個情境給你看>
> - **改不回來的地方**：<沒有／有，見下一項說明>
>
> 沒問題就回「同意」，我就開始做；想改哪裡直接說。

客戶改需求 → 照 builder 更新計畫，再給一次摘要。

**新開一支 app 時**：照 builder，計畫同意後才建 app。程式放一個新的 repo：`gh repo create <組織>/<名稱> --private`，
clone 到工作區（`setup.md` §3），照 builder Phase 2 建專案、在新 repo 的 `AGENTS.md` 寫專案做法，
並照 `project-setup.md` 加「客戶協作」一節。客戶的 GitHub 帳號沒有建 repo 的權限 → 請工程師建好再繼續（`engineer-collab.md` §3.1）。

## 4. 改不回來或影響大的選擇（builder 標「不可逆」的地方）

builder 遇到這些會提醒；你用下面的說法講給客戶，**讓客戶自己決定**：

| builder 的選擇 | 白話說法 |
|---|---|
| 新 app 是內部用還是給外部的人用（`access_mode`，建立後不能改） | 「這像決定大門開在公司裡面還是開在街上，蓋好就不能移。內部用＝只有登入的同事進得來；外部用＝客戶或廠商也能用他們的帳號進來。」 |
| 加在現有的系統，還是新開一支（builder 的 app 分配表） | 「加在現有的：同事從同一個入口進去，資料、權限跟現在的共用，改動影響現有畫面。新開一支：入口、權限、程式都分開，比較好管理，但同事要多記一個入口、共用的資料要另外接。」（照 builder 的功能群拆分判斷給建議，讓客戶選） |
| 一般 app 還是容器 app（產品線） | 「一般 app 是在平台上直接做；容器 app 是把整套原本的系統搬進來跑。選了之後要換，等於重做一次。」 |
| 新帳冊的名稱（自建表實體名，建立後不能改） | 「帳冊的『內部編號名稱』建好就不能改，我會用英文取一個清楚的名字，畫面上顯示的中文名稱之後還能改。」 |
| 刪掉一個背景處理（發布時移除 action） | 「這個處理拿掉後，原本用到它的按鈕或排程會失效，要確定沒有地方在用。」 |
| 發布時開「失敗自動退回」 | 「如果新版上線後檢查沒過，會自動換回上一版，大家用的還是舊版。」 |

## 5. 寫入正式資料（builder 資料操作線 §3.5 寫入閘門）

builder 的四步是：估影響面 → 備份 → 試一筆 → 確認。跟客戶這樣講：

> 這次要改的是大家正在用的真實資料，沒有復原鍵，所以我分四步：
> 1. 先算會動到幾筆：<N 筆，例：3 月份全部的請假>
> 2. 先把這些資料備份一份到你電腦（放在 <路徑>，不會放進專案）
> 3. 先改 1 筆給你看：<哪一筆、改成什麼>
> 4. 你看過說可以，我再改剩下的
>
> 要開始嗎？

只是查詢或匯出不用這四步；匯出的檔案放在 repo 以外（`setup.md` §3 的工作區 `exports/`），告訴客戶檔案在哪、裡面有個資。

## 6. 成員與權限（builder `member-admin.md`）

> - **邀請同事**：「我會寄一封邀請信到 <email>，他點信裡的連結註冊後就能登入。邀請 48 小時後失效，到時沒點要重寄。要寄嗎？」
> - **開或改權限（角色）**：「<某人> 會變成可以 <看到／改到> <哪些資料>。像換一張門禁卡，換了馬上生效。要換嗎？」
> - **系統只開放給某些角色（app 角色白名單）**：「之後只有 <哪些角色> 的人打得開這支系統，其他人打開會說找不到。」

寄信、改權限前都先確認收件人與內容；email 由客戶提供，不寫進 issue 或 PR。

## 7. 接外部服務（builder Action 硬規則 5）

builder 要求先說清楚「連到哪、送出哪些資料、哪個功能用」並單獨取得同意。白話：

> 這個功能要跟 <LINE／Google／某某系統> 接線：
> - 會連到：<網域，例：api.line.me>
> - 會送出：<哪些資料，例：申請人的 LINE 帳號代碼、假別、日期；不送身分證或薪資>
> - 用在：<哪個功能，例：請假核准後通知申請人>
> - 需要一把鑰匙（金鑰）：<從哪裡拿，例：LINE 官方帳號後台>。鑰匙由你自己放，不要貼在對話裡。
>
> 同意這樣接線嗎？

金鑰怎麼放照 builder（`custom-app-dev-guide.md` §25.2）：Windows 請客戶在 Builder 的「服務」分頁自己貼上；
macOS／Linux 可以由你開好權限 600 的檔案、客戶自己貼，再用 builder 的腳本寫入。帶客戶做時講清楚點哪裡、貼在哪一格。
建立外部服務或寫金鑰要有權限（builder 有寫），403 就請有權限的人（租戶管理者或 app 擁有者）來做。

資料或網域之後有變，要再問一次。

## 8. 發布前後（builder Phase 4.4 與專案的發布流程）

發布前：

> 接下來要把新版放上大家在用的網址，所有同事都會用到。這次改的是：<一兩句>。
> 我已經在 <草稿版／本機> 驗收過：<一句話>。要上線嗎？

builder 或專案的發布工具發現**線上版本有別人剛發布、還沒收進專案的修改**時，照專案的處理方式（通常是先停下來），跟客戶說：

> 線上的版本跟我們手上的不一樣，可能是工程師剛好也發布了新版。直接上線會蓋掉他的修改，我先 <照專案的處理方式>。

被擋下時給客戶選項，讓他決定：
> 1. 等工程師把他的版本收好再上線（我在 issue 或 PR 上 @他，說我們在等）
> 2. 請工程師一起看要怎麼合（開請協助的單子）
> 3. 先不上線，我把做好的存起來，之後再說

發布後：到正式網址操作驗收，回報「上線了，我在正式網址試過 <情境>，結果正常」。

## 9. 平台問題回報（builder「問題回報」第 4 步）

builder 判定是平台本身的問題、要問使用者要不要送給 AI GO 開發團隊時：

> 我查了一輪，這看起來是 AI GO 平台本身的問題，不是我們系統的程式。
> 我整理了一份回報給 AI GO 的開發團隊：<兩三句白話摘要：在哪裡、做了什麼、發生什麼>。
> 要送出嗎？送出後我會給你追蹤的網址。

## 10. skill 更新失敗

照 builder Phase -1：把腳本印的手動指令由你執行；需要客戶做的（例：授權、重開 AI 工具）講清楚步驟。
有「破壞性變更」警語時，跟客戶說「不更新的話，之後 <會發生什麼>」，處理好再繼續。
