# 跟工程師協作

工程師是**隊友，不是關卡**。客戶可以自己完成從需求到上線的每一步；找工程師是為了**更快、更穩、讓大家知道彼此在做什麼**，
不是因為客戶「不能做」。

## 1. 什麼時候值得找工程師（建議）

| 情況 | 為什麼值得找 | 怎麼找 |
|---|---|---|
| 同一個問題試了兩輪還沒解開 | 換人看通常更快，客戶不用一直等 | 請協助 issue（§3.1），附上查到的 |
| 業務規則會影響其他系統或其他部門 | 工程師知道哪些地方共用同一份資料 | 先知會（§3.2），照常做 |
| 想先請人看過再上線（改動大、第一次做這類功能） | 多一雙眼睛 | PR 請審閱（§3.3） |
| 技術做法有好幾種，客戶拿不定主意 | 工程師知道長期維護的代價 | 請協助 issue，列出選項 |
| 專案 `AGENTS.md`「客戶協作」一節列在「希望先知會」的事 | 工程師事先說好的 | 知會（§3.2） |

這些都是建議：客戶想自己做下去就做下去，只要照 builder 與專案的做法、驗收過。

## 2. 兩種管道

| 問題在哪 | 管道 | 誰處理 |
|---|---|---|
| **這支 app**：需求、程式的問題、想請工程師看、交接 | 專案 repo 的 issue 或 PR（`gh`） | 專案的工程師 |
| **AI GO 平台本身**：平台的功能壞了、文件跟實際不符 | aigo-builder 的「問題回報」（`report_issue.py`） | AI GO 開發團隊 |

分不出來時先當成「這支 app」開 issue，工程師會判斷要不要轉給平台。

## 3. 範本

標籤不存在時先建立（`--force` 已存在也不會出錯，Windows／macOS 都能跑）：

```bash
gh label create "請協助" --color D93F0B --description "客戶協作：請工程師協助" --force
gh label create "知會" --color C5DEF5 --description "客戶協作：讓工程師知道，不用等回覆" --force
gh label create "研究任務" --color 1F80FF --description "客戶協作：請客戶與 AI 研究後回覆" --force
```

建標籤要 repo 的寫入權限；沒有就不加標籤，直接開。**每一份都先給客戶看草稿，說可以才送**——它們代表客戶發言。
工程師的 GitHub 帳號寫在專案 `AGENTS.md` 的「客戶協作」一節；沒寫就不指派，內文最後加一行「（專案還沒寫工程師聯絡方式）」。

### 3.1 請協助（issue）

標題：`【請協助】<一句話>`，例：`【請協助】請假送出一直失敗，試兩輪還沒解開`

```markdown
## 想做的事（白話）
<誰、在哪個畫面、做什麼、之後要看到什麼>

## 想請你幫的
<例：一起看原因／決定用哪個做法／接手做完>

## 已經做的
- 查到的：<相關程式位置、決策編號、錯誤訊息（去掉個資）>
- 試過的：<做法與結果>
- 做到一半的：<沒有／分支 `xxx`，已推上 GitHub，草稿 PR #N>
- 正式版有沒有受影響：<沒有／有，說明>

## 我這邊接下來
<例：先做別的事，等你回覆／這段期間先用 Excel 記>
```

```bash
gh issue create --title "【請協助】…" --body-file <草稿檔> --label "請協助" --assignee <工程師帳號>
```

### 3.2 知會（issue 或 PR 留言）

讓工程師知道，**不用等他回覆**。已經有 PR 就在 PR 說明裡 @他；沒有就開一張短 issue：

```markdown
@<工程師帳號> 知會一下：<做了什麼／要做什麼>，會影響到 <哪裡，例：做帳工作台也在用的員工資料>。
預計 <什麼時候> 上線，有疑慮再跟我說。
```

### 3.3 請審閱（PR）

PR 照專案的格式寫，另外：

```bash
gh pr edit <PR 編號> --add-reviewer <工程師帳號>
```

跟客戶說：「我請工程師看一下，他看過或 <專案約定的時間> 沒回覆，我們就照原計畫上線。」等不等由客戶決定。

### 3.4 交接（做到一半請工程師接）

1. 把改到一半的存成一個版本，推上 GitHub：`git push -u origin <分支>`。
2. 開草稿 PR（`gh pr create --draft`），說明寫：做到哪、還差什麼、驗收情境。
3. 開請協助 issue，連到草稿 PR。
4. 跟客戶說：「我把做到一半的整理好交給工程師了，正式版沒有變。」

## 4. 工程師回覆之後

客戶說「工程師回了」或接續上次時，讀 issue／PR 的留言（`gh issue view <網址> --comments`），用三句白話講工程師說了什麼、
接下來要誰做什麼。工程師給的做法照樣走功能流程（builder 加本 skill 的驗收）。

## 5. 研究模式（工程師發來的請求）

工程師用「研究任務」請客戶（和他的 AI）研究、訪談、整理業務規則或需求，結果回貼到 issue。

### 研究任務格式（工程師開 issue 時用）

標題：`【研究任務】<要研究的事>`，例：`【研究任務】整理事務所現在的加班申請與核准方式`

```markdown
## 背景（給客戶看的白話）
<為什麼要研究、研究完會拿來做什麼>

## 要回答的問題
1. …
2. …

## 已經知道／已經排除的
<工程師已經查過的，不用再查>

## 給 AI 的指令
- 研究方式：<訪談客戶／讀程式與文件／整理客戶提供的檔案／用 Chrome 擴充套件看某個系統／混合>
- 要讀的地方：<檔案路徑、文件、相關 issue>
- 要問客戶的：<問題清單，或「依要回答的問題自行訪談」>
- 交回格式：照 aigo-client-collab 的「研究結果」格式；另外需要：<表格、流程、範例…>

## 期限
<希望什麼時候前回覆；沒有就寫「不急」>
```

「給 AI 的指令」是客戶的 AI 主要照做的區塊，其他是背景。

### 流程（客戶貼了研究任務的網址）

1. **讀**：`gh issue view <網址> --comments`。讀不到（權限、網址錯）→ 跟客戶說原因，請他確認網址或請工程師開權限。
2. **確認範圍**：用三句白話跟客戶講「工程師想知道什麼、我們要怎麼查、大概要問你幾題」。
   issue 不是這個格式也沒關係，照內容判斷；看不懂就問客戶，或在 issue 留言請工程師補（客戶說可以才留）。
3. **研究**：
   - 訪談客戶：用業務的語言問，可以一次列出幾題讓客戶照編號回答，例：「同事要加班時，現在是先口頭說，還是先填單？」
     客戶說「要問別人」就記成待確認。
   - 讀程式與文件：講程式的行為時以實際程式為準。
   - 客戶提供的檔案（Excel、PDF、截圖）：只取結構與規則，不把裡面的真實資料抄進結果。
4. **整理**成下面的格式，先給客戶看，問「這樣寫對嗎？有沒有要改的？」
5. **回貼**：客戶說可以才留言：`gh issue comment <網址> --body-file <結果檔>`，回報留言網址。
6. 研究結果裡有建議做法，問客戶要不要接著做。

### 研究結果格式

```markdown
## 研究結果（客戶確認過）

### 結論
<三句以內回答 issue 的問題>

### 逐題回答
1. <問題> → <答案>（來源：客戶訪談／程式 `路徑`／客戶提供的檔案）
2. …

### 業務規則與例外
<整理出來的規則；例外情況各一句>

### 還不確定的
<客戶說要問別人、或查不到的；寫誰可以回答>

### 建議（若有）
<建議做法，標明是 AI 的建議>
```

## 6. 協作節奏

- 開工前先拿專案最新版（Phase 0 會做），工程師剛改的才不會被蓋掉。
- 一個功能一個 PR，PR 小、說明寫清楚驗收情境，工程師看得快。
- 決定了什麼照專案的方式記（例：`docs/DECISIONS.md`），下次客戶或工程師的 AI 都讀得到。
- 發布後在 PR 寫一句「已上線、怎麼驗收的」，工程師不用來問。
